# 개발·출시 로드맵

현재 목표는 [제품 원칙](../PRODUCT_VISION.md)의 Host-Native 확장이다. 날짜 약속 대신 증거 기반 통과 조건으로 진행하며, 구현·검증 상태는 [progress](progress.md)에만 기록한다.

## 사용자 경험 수락 기준

[핵심 사용자 경험](../PRODUCT_VISION.md#핵심-사용자-경험)의 UX-01~UX-05를 개발·검토의 공통 ID로 사용한다. 아래는 기존 수용 게이트에 적용할 사용자 관점의 기준이며, 게이트 선행 관계와 Policy·Capability·승인·예산을 유지한다. 구현 상태는 [사용자 경험별 진행도](progress.md#사용자-경험별-진행도)에서 확인한다.

| ID | 실제로 확인할 수락 시나리오 | 거부·실패 확인 |
| --- | --- | --- |
| UX-01 | 자연어 요청과 대상 저장소에서 필요한 정보를 확인하고, 누락된 범위·완료 기준·선택만 질문한다. 사용자가 내부 JSON·명령을 조립하지 않아도 검토 가능한 계획·검증 방법이 준비된다. 충분한 정보가 있는 요청에서는 불필요한 질문이 없어야 한다. | 모호한 완료 기준을 임의 확정하거나, 계획 검토를 실행 승인으로 취급하지 않는다. |
| UX-02 | 이미 승인된 적격 작업은 매번 “계속” 지시 없이 진행한다. 새 결정이 필요하면 이유·선택지·권장안·영향과 대기 중인 작업을 보여주고 답변을 해당 계약에 반영한다. | 새 권한·범위 확대·중요한 선택·예산 소진에서 묵시적 승인을 만들지 않는다. 사용자 미응답을 승인으로 간주하지 않으며, 안전한 중단은 질문 묶음을 기다리지 않는다. |
| UX-03 | 실제 실패를 기록하고 가설·허용 수정·새 후보·독립 재검증을 연결한다. 별도 승인이 필요한 수정은 요청하고, 한도 내 복구 또는 근거 있는 차단 보고까지 확인한다. | 반복 실패·무진전·권한 변경·예산 소진·불확실한 효과에서 멈춘다. 테스트·완료 기준·보호 수준을 낮춰 성공시키지 않는다. |
| UX-04 | 중간 체크포인트와 세션 경계 뒤 “이어서 해 줘” 요청으로 기존 목표·작업·결정을 찾고, 파일·승인·lease·시도·예산·증거를 대조해 다음 적격 행동을 제시하거나 실행한다. 재입력은 누락·충돌·새 결정에 한정한다. | 승인 철회·소스 변경·진행 중 시도·미확정 효과·기록 누락을 포함해 중복 실행·예산 초기화·오래된 완료 표시가 없어야 한다. 실제 Host 새 세션/Compaction은 프로세스 재시작과 별도로 관측한다. |
| UX-05 | 실제 대상에 반영된 후보를 관측하고 완료 기준별 충족/미충족, 검증 명령·종료 코드·실패/제외/미실행, 결과 위치·남은 한계·필요한 다음 행동을 제시한다. 부분 완료와 취소도 확인한다. | AI 자기 보고·미반영 후보·오래된 증거·0건/누락 검사로 전체 완료를 만들지 않는다. Local과 Protected 판정 및 사용자 확인이 필요한 조건을 구분한다. |

### 개발과 검증에 적용하는 방법

- WorkItem에는 대상 UX ID, 현재 불편과 기대 변화, 파일 범위·선행 조건·완료 기준·검증 명령·필요 승인을 연결한다. 모듈 분리는 해당 경험을 구현하거나 검증하는 데 필요한 범위로 제한한다.
- 첫 사용자 흐름 시험은 승인된 작은 작업에서 UX-01 → UX-02/UX-03 → UX-04 → UX-05를 연결한다. 수정 가능한 파일·허용 명령·Backend·중단 지점·복구 시도·예산과 실패/차단 시나리오를 실행 전에 고정한다. 작업에 실패 상황이 없으면 UX-03은 별도 실패 사례로 확인하고 미실행으로 남긴다.
- Host·모델/버전·OS·셸·기준 커밋·계약 revision·후보·승인·증거 참조를 기록하고, 사람이 작성한 JSON/명령·반복 설명·승인/복구 개입을 포함해 실제 사용자 부담을 측정한다. 가용 비용과 unknown을 구분하며 개선 판단 기준은 비교 전에 정한다.
- 부품 시험·설치 시험·Local 시험·실제 Host 전체 흐름을 각각 보고한다. 같은 계약의 연결된 근거가 없으면 개별 성공을 조합해 전체 수용으로 표시하지 않는다. 기본 Host 단일 Agent 비교와 선택적 Multi-Agent 비교는 아래 기존 기준을 따른다.

이 문서화는 새 실행 승인을 부여하거나 기존 Task 계약을 변경하지 않는다. 실제 구현·시험에서 범위나 수락 기준이 바뀌면 기존 revision 또는 새 작업 경로로 검토·승인하고 영향을 받는 후보를 재검증한다.

## 현재 Host-Native 후속 작업

아래 순서는 수용 게이트의 선행 관계다. 오프라인 시험·플랫폼 조사·측정 설계는 병행할 수 있으나 앞선 게이트의 실제 근거 없이 후속 수용을 완료로 표시하지 않는다. 기존의 기본 Host 사용·Live·독립 검증 항목은 아래 경로로 통합한다.

| 작업 | 선행 조건 | 수락 기준과 남은 검증 |
| --- | --- | --- |
| 신규 프로젝트 Bootstrap | 목표·범위·검증 기준과 파일/Git 효과의 승인 경계 | 기존 오프라인 구현을 재사용. Git HEAD 없는 디렉터리에서 probe→Draft→Validator→DAG→승인 fileset→Local 검증을 재현하고 기존 파일 보존·실패·중단·재개·기존 프로젝트 회귀를 확인. Git 초기화·최초 커밋은 별도 권한으로 처리하며 Host Live 수용은 다음 게이트에 연결 |
| Codex·Claude Host Live 수용 | Bootstrap 재현, 각 Host의 실제 Capability와 승인/격리 경계 확인 | 각 Host에서 기존 모델·인증·세션의 설치·발견·실제 호출을 구분해 관측하고 단일 Agent로 목표→검증을 수행. 기본 준비에 Docker·WSL·별도 OS 계정·직접 API Key를 요구하지 않음. 현재 공개 보호 실행 차단은 근거 없이 우회하지 않음 |
| 실제 WorkItem 구현·검증 | 해당 Host Live 경로와 검증 Backend의 준비 | 승인된 실제 작업에서 범위·의존성·수락 기준에 따라 구현하고 계약/후보에 결합된 Evidence/Judge 결과 확보. 실패·누락·변조가 수락되지 않음을 확인. Local / Container / Host Sandbox 보장 범위를 유지하며 Local 성공을 Protected 완료로 승격하지 않음 |
| 역할별 Agent 위임·협업 | 단일 Agent WorkItem의 실행·검증 근거 | Host가 제공하는 Agent/Subagent로 명시적 역할·범위·입출력 위임을 관측. Coordinator의 의존성·자원/파일 충돌·병렬 후보·직렬 통합 및 통합 후 검증 확인. 역할 metadata·Fake 성공은 Live 위임 증거에서 제외 |
| 제한된 자동 오류 수정·재검증 | 실제 WorkItem 실패 근거와 승인된 수정/예산 한도; 협업 경로는 위임 게이트도 충족 | 실패→가설→허용 수정→새 후보 재검증을 관측. 반복 실패·무진전·권한 변경·예산 소진에서 중단하고 테스트/수락 기준을 보존. 기존 Bootstrap repair를 범용 자동 루프 완료로 취급하지 않음 |
| 장기 실행·중단·복구 | 선택한 단일/협업 경로와 제한된 개선 루프 수용 | 기존 Persistent State·Work Log·Lease·Recovery로 실행/검증/확정 경계의 중단·재시작·취소·lease 상실·미확정 효과를 확인. 오래된 결과 확정·중복 효과·예산 초기화가 없고 기존 증거가 보존됨 |
| Cross-Platform 실사용 검증 | 대표 실행·복구 시나리오와 환경별 Capability 목록 | Windows·macOS·Linux별 Host/버전/셸/Backend와 통과·실패·미시험을 기록. 공백/비ASCII 경로·줄바꿈·명령 인자·프로세스 종료·권한·재개를 실측. Docker 없는 기본 경로와 선택 보호 Backend를 분리하며 한 OS 결과로 전체 지원을 선언하지 않음 |
| Todo + Calendar MVP·비즈니스 성과 | 위 수용 게이트를 통과한 대상 환경, 사용자 승인 범위, 기능 시나리오와 비교 기준선 | Todo 생성·수정·완료·삭제와 Calendar 날짜/일정 표시·변경 및 두 기능 연결의 범위를 사용자와 고정하고 실제 사용자 흐름으로 검증. 데이터 보존·오류/재개·회귀·최종 사용자 검토 포함. 회사/사이드 프로젝트에서 준비·개입·검토 시간, 품질·재작업, 측정 가능한 비용을 비교하고 성공·실패·취소와 표본 한계를 공개. 현재 MVP 완성 또는 생산성 개선 실적을 뜻하지 않음 |

Bootstrap의 오프라인 구현은 완료 기능으로 취급하되, Host Live·보호 검증이 끝나기 전에는 수용 완료로 표시하지 않는다. 보호된 실행과 외부 효과는 현재 Policy·Capability·승인을 만족해야 하며, 위 작업 목록 자체는 실행 승인이 아니다.

사용자 수용·패키지 공개 범위는 위 실사용 게이트와 아래 M4/M5의 기존 출시 조건을 함께 적용한다. 과거 Alpha 실적, 운영자 보조 실행, 독립 사용자 온보딩을 분리하며 공개 패키지나 문서 갱신 자체를 성과로 세지 않는다. 새 플랫폼·업무 연동은 이 표만으로 승인되지 않는다.

### 기존 게이트에 적용할 지속성·복구·비교 수용 조건

아래 조건은 위 게이트의 완료 증거를 보강하며 별도 개발 단계가 아니다. 기존 계약의 오프라인 구현과 아래 Host Live 수용 목표를 구분한다. 이 문서의 추가만으로 게이트를 통과 처리하지 않는다.

| 조건 | 연결할 기존 게이트 | 수락에 필요한 근거 |
| --- | --- | --- |
| Goal Persistence | 실제 WorkItem 구현·검증, 제한된 자동 오류 수정·재검증, 장기 실행·중단·복구 | 필수 조건이 남은 상태에서 Turn·Attempt·세션을 끝내도 Objective가 완료로 표시되지 않음. 승인과 예산이 남으면 다음 적격 작업으로 이어지고, 중단 시 미충족 조건·근거·이유·다음 허용 행동을 인계. 완료는 전체 필수 조건과 해당 계약의 Evidence/Judge로만 판단하며 취소·예산 소진을 성공으로 바꾸지 않음 |
| Context Compaction Recovery | Codex·Claude Host Live 수용, 장기 실행·중단·복구 | 각 Host에서 압축 및 새 세션 재개 전후의 계약/revision·승인·DAG·영속 상태·고정 Context·lease·미확정 효과·예산·Evidence 참조를 대조. 필수 기록 누락/충돌, 진행 중 Attempt, 취소·철회 사례에서 중복 효과·예산 초기화·잘못된 완료가 없음. 오프라인 프로세스 재시작은 보조 근거이며 실제 Host 압축 근거를 대신하지 않음 |
| Contract Revision Synchronization | 실제 WorkItem 구현·검증, 역할별 Agent 위임·협업, 제한된 자동 오류 수정·재검증 | 실행 전/중 요구 변경의 범위·의존성·Context·테스트·승인·Evidence 영향을 기록. 기존 revision 제약에 따라 영향 작업을 보류하고 새 revision 또는 새 Task/Workflow로 검토·승인. 오래된 응답/승인/후보 증거의 재사용 거절, 영향 작업과 통합 후보 재검증, 무관한 작업의 권한 보존 확인. 자동 영향 분석 완료를 가정하지 않음 |
| Single-Agent Baseline | 역할별 Agent 위임·협업, Cross-Platform 실사용 검증, Todo + Calendar MVP·비즈니스 성과 | 기본 Host 단일 Agent / CodeFleet 단일 Agent / CodeFleet Multi-Agent를 동일 작업 집합·초기 코드/데이터·수락 기준으로 비교. Host별로 구분하고 모델/버전·도구·OS·Backend·승인/예산 조건을 고정하거나 차이를 공개. 실제 완료 품질을 같은 독립 검사로 평가하고 조정·검토 비용을 포함해 시간·품질·비용을 보고 |

비교 전에 대상 작업, 반복 방식, 수락 품질과 개선 판단 기준을 정한다. 전체 경과 시간과 사람의 준비·개입·검토 시간, 필수 조건 통과·결함·회귀·재작업, 가용 토큰/비용 및 위임·통합 부담을 기록한다. 성공만 선별하지 않고 실패·중단·취소와 표본 수·변동을 함께 보고하며 측정값·공급자 보고·추정·unknown을 구분한다. 측정 불가능한 비용은 영으로 대체하지 않는다. 단일 Agent를 기본으로 유지하고 Multi-Agent의 실익이 관측됐을 때만 해당 작업군에서의 적용 근거로 삼는다. 비교 계획은 모델 호출·위임·외부 효과를 승인하지 않는다.

## 초기 Alpha 출시 계획의 적용 범위

아래는 2026-09-30에 작성한 초기 Alpha의 단계·요구 ID·출시 조건이다. 과거 실행 근거와의 연결을 보존한다. 현재 Host-Native의 다음 작업은 위 표가 정의하며, 아래 초기 직렬 실행 범위나 PR 전달 중심 목표를 기본 Host 기능 전체의 제한으로 확대하지 않는다.

## 단계와 의존성

`M0 기준선 → M1 한 작업의 신뢰성 → M2 자율 루프·복구 → M3 PR 전달 → M4 공개 알파·파일럿 → M5 공개 사용 릴리스`

문서가 많아진 것을 진척으로 세지 않는다. 각 단계는 실행 가능한 제품 동작과 반증 테스트로 닫는다. 공개 준비 자료는 앞 단계부터 작성하되 사용 가능하다는 표시는 릴리스 게이트 통과 후 붙인다.

## M0 — 범위와 현 상태 확정

| 작업 ID | 작업 | 산출물·완료 기준 |
| --- | --- | --- |
| M0-T1 | 기존 전체 검사와 실제 저장소 작업 재현 | 커밋·환경·명령·종료 코드·우회·실패 기록. 과거 결과와 분리 |
| M0-T2 | 지원 환경·첫 어댑터 선정 | 사용자 개발 환경 우선으로 인증·편집·검증·wrapper·중단·관측 가능성 시험 |
| M0-T3 | 공개 저장소·라이선스·후속 프로젝트 관계 결정 | 유지보수할 저장소, 사용 허용 조건, 이관 범위, 브랜드 결정 기록 |
| M0-T4 | 기능 계약과 위험 범위 고정 | R01~R18에서 첫 출시 포함/제외 확인, 대상 작업 집합과 평가 절차 등록 |
| M0-T5 | 미해소 결함 재분류 | 실행·검증·권한·반영 관련 항목을 현재 코드 기준으로 재현. 과거 등재부 수정 대신 연결 기록 |

출구: 대표 작업의 현재 실패를 재현할 수 있고 지원할 실행 경로가 선정돼 있다. 이 단계의 결과가 기존 계획과 다르면 아키텍처를 먼저 수정한다.

## M1 — 신뢰할 수 있는 한 작업

| 작업 ID | 작업 | 산출물·완료 기준 |
| --- | --- | --- |
| M1-T1 | 모듈 경계·스키마·저장 계층 최소 구현 | 계약→실행→증거→판정을 한 경로로 연결. 증거 replay 판정 일치 |
| M1-T2 | 역할·기능별 권한과 환경 진단 | 역할 바꿔치기 없이 편집·검증. 실제 허용·거부 양쪽 시험 |
| M1-T3 | 독립 검증·보호된 기준 | 올바른 구현 성공, 잘못된 구현·테스트 누락·검증 자산 변조 실패 |
| M1-T4 | 지원 실행 격리와 비밀 경계 | 에이전트의 정책·증거 저장소 및 PR 자격증명 접근 차단 확인 |
| M1-T5 | 실제 저장소 수직 실행 | 작은 실제 변경을 우회 없이 반복 완료하고 변경·검증 증거 보존 |

출구: 프로세스 종료와 업무 완료가 분리되고, 검증한 변경을 식별할 수 있다. 모든 플랫폼을 한 번에 지원하지 않는다.

## M2 — 자율 실행과 예외·복구

| 작업 ID | 작업 | 산출물·완료 기준 |
| --- | --- | --- |
| M2-T1 | 지속 실행 컨트롤러·위임 정책 | 정상적인 대상 작업을 명령 재입력 없이 처리. 철회·만료 정책 거부 |
| M2-T2 | 예산·재시도·무진전 탐지 | 실패별 복구 분기. 한도 이후 새 시도 없음. 비용 미측정 표시 |
| M2-T3 | 영속 상태·lease·재시작 | 실행·검증·확정 경계별 강제 종료와 재시작 시험. 중복 확정 없음 |
| M2-T4 | pause/resume/cancel·예외 UX | 중단 중 실행 상태와 부분 효과 보존. 필요한 결정·증거를 한 보고서에 표시 |
| M2-T5 | 작업 초안·맥락 manifest | 필수 조건 미해결 시 질문. 출처·revision 변화 시 재검사 |

출구: 성공 경로뿐 아니라 실패·재개·취소 경로가 재현 가능하다. 사람의 개입 요청을 측정하기 시작한다.

## M3 — 검증한 변경을 PR로 전달

| 작업 ID | 작업 | 산출물·완료 기준 |
| --- | --- | --- |
| M3-T1 | 전달 계획·원격 권한 분리 | PR 전 변경 대상과 공개될 본문·증거가 결정됨. 허용 저장소만 쓰기 |
| M3-T2 | 브랜치·PR 생성 | 검증 head와 PR head 일치. 변경 이유·검증·남은 한계 첨부 |
| M3-T3 | 효과 요청 outbox·재조정 | PR 성공 후 응답 유실·재시작에도 기존 PR을 찾아 중복 생성 방지 |
| M3-T4 | base 변경·충돌·원격 실패 처리 | 재검증 또는 예외. 오래된 수락으로 변경 반영하지 않음 |

출구: 목표 입력부터 PR까지 자동 진행하고 사용자는 예외와 최종 결과를 확인한다. 자동 병합·배포는 아직 제외한다.

## M4 — 공개 알파와 실제 사용자 파일럿

| 작업 ID | 작업 | 산출물·완료 기준 |
| --- | --- | --- |
| M4-T1 | 설치 가능한 패키지·진단·제거 | 깨끗한 지원 환경에서 설치·예제 완주·제거. 로컬 개발 소스에 의존하지 않음 |
| M4-T2 | CI·배포 smoke·업데이트 | 지원 환경 전체 검사 통과, 배포 패키지 설치 시험, 상태 schema 호환 검증 |
| M4-T3 | 공개 자료·권리·정보 점검 | 사용 가능한 LICENSE, README/quickstart, 지원 범위, 한계, contribution/security 안내, 비밀·개인정보 점검 |
| M4-T4 | 운영 절차 | 이슈 양식, 재현 정보 내보내기와 비밀 제거, 버전별 변경·지원 종료·취약점 대응 절차 |
| M4-T5 | 외부 파일럿 | 제안 목표: 개발자 외 사용자 최소 3명이 각자 설치·예제 완주, 합계 실제 작업 20건 기록 |

알파 공개 조건: M1~M3의 필수 기능과 안전 경계, 설치·라이선스·비밀 점검을 먼저 통과한다. 알파임을 명시하고 미지원 작업을 안내한다. 사용자에게 저장소와 로그를 자동 업로드하지 않으며 원격 측정은 명시적 opt-in으로 둔다.

파일럿 수치는 초기 목표 제안이며 실적이 아니다. 대상 모집이 어렵다면 낮춘 표본을 숨기지 않고 실제 표본과 불확실성을 보고한다. 적은 표본의 성공률을 일반 성능 보증으로 사용하지 않는다.

## M5 — 공개 사용 릴리스 판정

출시 증거 묶음은 커밋·패키지 버전·지원 환경·검증 명령 종료 코드·반증 결과·파일럿 원자료·알려진 한계를 포함한다.

| 게이트 | 통과 조건 |
| --- | --- |
| 기능 | 지정 작업의 입력→검증→PR 흐름이 수동 우회 없이 작동 |
| 품질 | 등록 평가 집합에서 잘못된 자동 수락이 발견되지 않음. 검증 누락·변조·오래된 head 반증 테스트 통과 |
| 복구 | 주요 단계 강제 종료·응답 유실·정책 철회·예산 초과 시험에서 중복 반영 및 성공 오표시 없음 |
| 설치 | 비개발자 환경에서 안내대로 설치·예제·제거 가능. 지원 환경 CI 통과 |
| 생산성 | 비교 가능한 작업 집합에서 사람 개입 시간이 감소하고 품질 저하 여부와 비용을 함께 보고 |
| 공개 | 사용 허용 조건, 권리, 개인정보·비밀, 이슈·보안 대응 준비 완료 |
| 설명 | README의 현재 기능과 제한이 실제 패키지와 일치. 설계·예정 기능과 구분 |

위 기준은 유한 평가 집합에 대한 출시 판단이며 무결함 보증이 아니다. 효과가 확인되지 않으면 범위와 검증을 조정하고 다시 평가한다. 지표 개선 없이 단순히 알파 표지만 제거하지 않는다.

## 작업 진행 규칙

1. 한 번에 검증 가능한 수직 슬라이스 하나를 선택한다. 요구 ID와 수락 조건을 먼저 지정한다.
2. 해당 작업의 현재 운영 문서를 사용자와 명확히 정하고, 필요 시 bounded preflight를 수행한다. 역사 전체의 자동 감사로 구현 허가를 대신하지 않는다.
3. 구현·반증 테스트·실행 근거·진행 상태를 같은 변경에서 갱신한다.
4. 실패하면 증거를 남기고 설계 오류·구현 오류·환경 미지원으로 분류한다. 기준 완화로 성공 처리하지 않는다.
5. `progress.md`의 상태는 증거 링크가 있을 때만 VERIFIED로 바꾼다. 역사 문서에 현재 상태를 복제하지 않는다.

## 후속 확장

첫 사용자 경험과 유지보수 부하가 확인된 뒤 다중 저장소·동시 작업·팀 권한·웹 UI를 검토한다. 자동 병합·배포에는 별도 영향 평가와 복구 계약이 필요하다. 회사 업무 커넥터는 읽기·초안 생성부터 시작하고 외부 전송·금전·데이터 변경은 업무별 권한·검증·중복 방지 계약을 새로 정의한다.
