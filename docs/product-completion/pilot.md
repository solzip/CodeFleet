# 공개 알파·파일럿 운영 패킷

상태: MIT 공개 알파 파일럿 접수 준비. 참여자·실사용 실적 없음. [알파 설치 안내](alpha-quickstart.md)를 따라 사용한 뒤 [피드백 이슈](https://github.com/solzip/CodeFleet/issues/new)로 아래 피드백 양식을 복사해 결과를 제출한다.

## 참가 조건과 범위

자신이 수정·전송 권한을 가진 작은 Node 저장소, 이미 존재하는 실패 테스트, 지원 환경을 가진 개발자를 모집한다. 회사 코드나 고객 정보를 반드시 사용할 필요는 없다. 비밀이 없는 공개·개인 예제로 설치 경험부터 확인한다.

모집 목표는 개발자 외 사용자 최소 3명, 합계 실제 작업 20건이다. 이는 아직 달성하지 않은 초기 평가 목표다. 실제 참여와 실행 기록만 집계하며 개발자의 자체 실행이나 자동 fixture를 외부 사용자 실적으로 세지 않는다.

## 참가 순서

1. 지원 범위·라이선스·Claude로 전송하는 맥락과 비용을 읽는다.
2. 배포한 패키지를 빈 환경에 설치하고 doctor 결과를 확인한다.
3. 실패 테스트가 있는 작업 하나를 고르고 수동으로 할 때의 예상·실제 기준선 기록을 마련한다.
4. 로컬 전달 모드로 첫 작업을 실행하고 검증 결과를 확인한다.
5. 원하면 자신의 저장소에 draft PR 전달을 시험한다. 병합은 본인이 판단한다.
6. 아래 양식으로 아래 피드백 양식을 복사해 결과를 제출한다. 로그·원문은 기본 수집하지 않는다.

## 피드백 양식

```text
참가자 익명 ID:
패키지 버전 / OS / Node / Docker / Claude 버전:
작업 유형 / 난이도 / 테스트 수:
설치 성공 여부 / 설치에 걸린 시간:
요청 준비 시간 / 질문 응답 시간 / 결과 확인 시간 / 수동 복구 시간:
총 대기·실행 시간 / 시도 수:
결과: 완료 / 중단 / 취소 / 실패
품질: 수락 / 반려 / 재작업 / 회귀 발생 / 아직 미확인
비용: 공급자 보고값 / 알 수 없음
막힌 단계와 오류 요약:
같은 작업의 비교 기준선과 비교 방법:
선택적 PR URL (공개 가능할 때만):
```

원문·전체 로그·상태 DB·계정 이메일·토큰을 제출하지 않는다. 추가 재현 자료가 필요하면 운영자가 비밀 제거 범위를 설명하고 개별적으로 요청한다. 익명화된 결과도 사용자가 공유하기로 선택한 것만 저장한다.

## 운영자 판정

- 모든 접수 작업에 ID를 부여하고 실패·취소도 분모에 포함한다.
- 설치 실패, 환경 미지원, 검증 결함, 모델 제안 오류, 제품 오류를 구분한다.
- 잘못된 자동 수락·권한 경계 침해가 있으면 해당 경로의 알파 사용을 중지하고 재현·수정·재검증한다.
- 결과가 좋지 않아도 작업 난이도를 사후 변경해 성공률을 높이지 않는다.
- 개입 시간 감소와 품질·비용을 함께 보고한다. 작은 표본을 일반 성능 보증으로 표현하지 않는다.

코드·설치 패킷 준비와 파일럿 완료는 다른 상태다. 실제 외부 사용이 없으면 파일럿 완료로 표시하지 않는다.
