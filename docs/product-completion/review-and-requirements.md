# 종합 검토와 제품 요구사항

작성일: 2026-09-30. 검토 대상: `ea72069b8cd9f1b17d6a1784eaa6f8ae4c950c31`의 문서와 소스. 상태: 정적 검토 및 신규 제품 제안.

## 검토 배경

사용자가 제시한 채용 공고는 AI Agent 중심 개발, 컨텍스트·하네스·루프 엔지니어링, Human-in-the-loop에서 Human-on-the-loop으로의 전환, 실제 배포·운영 경험을 요구한다. 이어 사용자는 이 프로젝트를 완성하고 공개하여 실제 사용자를 확보하겠다는 목표를 제시했다.

아래 사실은 소스에서 확인한 구조와 기존 실행 기록이다. 이번 문서 작성 중 제품 실행·성능·운영 결과를 새로 측정하지 않았다. 채용 적합성 평가와 제품 성숙도 평가는 구분한다.

## 채용 공고와 연결되는 경험

| 항목 | 프로젝트의 근거 | 평가·한계 |
| --- | --- | --- |
| 에이전트 중심 개발 | 작업 계약을 실행 어댑터에 위임 | 직접 관련. 작성자가 한 줄도 직접 코딩하지 않았다는 사실은 입증하지 못함 |
| 컨텍스트 엔지니어링 | 목표·역할·범위·제약·완료 조건·검증·상위 목표를 프롬프트로 구성 | 강한 연결. 맥락 선택·최신성·장기 작업 인수인계는 추가 설계 필요 |
| 하네스 엔지니어링 | 실행 격리, 정책 검사, 직접 검증, 자기 보고와 관측 증거 구분 | 가장 강한 연결. 선언된 정책과 실제 강제 범위를 재검증해야 함 |
| 루프 엔지니어링 | 작업 큐·리뷰·다음 작업 상태 관리 | 기반 존재. 지속 실행·복구·종료 조건까지 연결된 제품은 아님 |
| Human-on-the-loop | 저위험·완전한 증거 등 조건에 따른 자동 수락 판정 | 부분 구현. 다음 실행과 결과 반영은 별도 행위 |
| 배포·운영 | 로컬 CLI와 실행·감사 기록 | 실제 사용자 운영 실적은 이 저장소만으로 입증 불가 |
| 일하는 태도 | 실패, 미확인 범위, 종료 사유, 교훈을 기록 | 검증·책임 있는 정리의 근거. 생산성 성과와는 별도 |

근거 위치: [프롬프트](../../src/prompt.ts) `renderPrompt` (기준 커밋 28행), [자동 리뷰](../../src/auto-review.ts) `evaluateAutoReview` (50행), [CLI](../../src/cli.ts) 단일 작업 실행 (499행), [결과 반영](../../src/apply.ts) (1행), [검증](../../src/run.ts) `HARNESS_EXECUTED` 필터 (1780행).

## 현재의 사실과 불확실성

- [기존 실행 보고](../runs/2026-08-13/first-full-loop.md)와 [종료 보고](../archive/2026-08-13/ARCHIVE.md)는 통제된 fixture의 조건부 완주와 실제 Spring Boot 프로젝트의 미완주를 구분한다.
- 역할 상한, 관측 채널, 어댑터 편집 권한, CLI 옵션 관련 우회가 기록돼 있다. 새 구현 작업에서 재현 여부를 확인하기 전까지 현재 결함 해소를 선언하지 않는다.
- [README](../../README.md)의 테스트·CI·결함 수치는 과거 기록이다. 이를 현재 테스트 결과로 인용하지 않는다.
- 반복 실행·동시성·다중 사용자 검증과 사람 개입 감소의 정량 성과는 확보하지 못했다.
- `run.ts`의 책임 결합은 [소스 안내](../../src/README.md)에 종료 원인으로 기록돼 있다.
- 자동 리뷰 함수를 호출할 수 있다는 사실은 스케줄러가 이를 자동 호출하여 후속 작업을 수행한다는 증거가 아니다.

## 목표 행동

Human-in-the-loop에서는 작업 진행을 위해 사람이 반복 판단한다. 목표 제품에서는 사람이 목표와 위임 정책을 설정하고, 시스템이 그 범위에서 실행한다. 위험·불확실성·예산 초과는 예외로 전달한다. 승인을 없애는 것 자체를 성공 지표로 삼지 않는다.

정상 시나리오: 사용자가 작은 버그 수정 목표와 검증 조건을 지정 → 실행 가능한 계약 확인 → 격리 구현 → 보호된 기준으로 검증 → 정책 판정 → PR 생성 → 근거와 변경 요약 보고.

예외 시나리오: 요구가 모호하거나 검증이 불가능함 → 수행한 시도·막힌 이유·필요한 결정만 묶어 질문 → 답변으로 계약 또는 예외 결정 갱신 → 영향 있는 검증부터 재개.

## 성과 측정 규칙

| 지표 | 정의 |
| --- | --- |
| 사람 개입 시간 | 계약 준비·질문 응답·승인·수동 복구·결과 확인의 능동 작업 시간 합계 |
| 무개입 완료율 | 최초 위임 후 추가 사람 개입 없이 완료한 작업 / 사전 등록한 자동 처리 대상 전체 |
| 결과 품질 | 잘못된 자동 수락, 반려, 재작업, 회귀 오류를 각각 기록 |
| 리드타임 | 요청 접수부터 PR 생성 또는 종료까지. 대기와 실행을 별도 표시 |
| 성공 작업당 비용 | 평가 집합의 실패·재시도 포함 총비용 / 성공 작업 수. 성공 0이면 산출 불가 |
| 자동 복구율 | 사전에 정의한 복구 가능 실패 중 사람 없이 복구한 비율 |
| 질문 적절성 | 필수 예외와 불필요한 질문을 사후 분류. 미분류도 표시 |

작업 유형·난이도·OS·어댑터별로 분리한다. 실패·취소를 분모에서 사후 제거하지 않는다. 취소 사유를 별도 표시한다. 수동 기준선과 자동화 실험은 유사 난이도 집합으로 비교하고 반복 학습 효과를 기록한다. 모든 지표는 아직 미측정이다.
