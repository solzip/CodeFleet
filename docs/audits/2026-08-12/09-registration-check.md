### 1-a-i. 번호를 새로 주지 않은 두 항목의 근거

#1(사전 차단 부재)과 #2(에이전트 명령 preflight)는 **P0-1 자체의 구성 요소**다. P0-1이 [부분해소]인 이유가 바로 이 둘이므로, 별도 P1 번호를 만들면 같은 사실이 두 번호로 추적된다. 대신 SUMMARY 판정 요약의 P0-1 잔여 칸에 둘 다 명시적으로 적었다 — 이전에는 preflight만 적혀 있어 사전 차단 부재가 표에서 보이지 않았다.

#29~#31은 "무해"로 판정한 관찰이다. 판정이 곧 결론이므로 추적 대상이 아니다. 다만 이 문서에 남겨, 다음 감사가 "왜 등재하지 않았는가"를 다시 판단하지 않아도 되게 했다.

## 1-b. P1-20 ~ P1-31이 SUMMARY의 P1 표에 있는가

**대조 전 상태**: P1-20 ~ P1-25가 `| ID | 내용 | 성격 |` 3열 표에 있었다. 번호와 내용은 있었으나 **근거 열이 없었다** — 성격은 판단이지 근거가 아니다.

**대조 후**: 표를 `| ID | 내용 | 근거 | 출처 |` 4열로 바꾸고 P1-31까지 채웠다. 각 행의 근거는 grep 결과·측정값·실행 출력 중 하나이며, 출처 열이 그 사실이 적힌 항목 파일을 가리킨다.

| ID | 표에 있는가 | 근거 열 | 출처 열 |
|---|---|---|---|
| P1-20 ~ P1-25 | ✔ (기존 6건) | ✔ 추가함 | ✔ 추가함 |
| P1-26 ~ P1-31 | ✔ 신규 6건 | ✔ | ✔ |

`P1-24`만 출처가 항목 파일이 아니라 SUMMARY의 공격 재실행 절이다. 격리 Run에서 검증 커맨드가 만든 `env-seen.txt`가 `changedFiles`에도 `pathViolations`에도 없다는 실측에서 나왔고, 항목 파일에 별도 절을 갖지 않는다. 출처 열에 그대로 적었다.

### D-1 (MAX_PATH) — 확인 불가, 다시 측정함

지시는 `env-DESKTOP-ENGO922.md`의 D-1을 이어받으라고 했다. 그 문서는 존재하지 않는다:

```
$ grep -rn "MAX_PATH\|D-1" docs/ src/ test/
(해당 없음 — 260은 전부 줄 번호·바이트 수·SVG 폭)

$ git rev-list --all --objects | grep -i "env-\|engo"
(0건)
```

**원래 D-1이 무엇을 확인했는지 알 수 없으므로 인용하지 않는다.** 대신 이름이 가리키는 대상을 이 감사에서 직접 측정했다.

격리는 Run을 `<tmpdir>/codefleet-worktree-XXXXXX/<runId>/` 아래로 옮기므로 저장소의 모든 경로에 고정 접두가 붙는다. Windows의 기본 경로 한계는 260자다.

```
platform                  : win32
os.tmpdir()               : 30자
격리 트리 접두             : 71자
260자까지 남는 여유         : 189자   ← 저장소 상대 경로에 허용되는 길이
현실적 深경로 (Java 149자) : 총 221자 → 통과
  파일 체크아웃            : true
  읽기                     : true
  git status               : exit 0, stderr 없음
core.longpaths            : (unset)
```

**이 호스트에서는 재현되지 않는다.** 그러나 여유가 189자로 유한하고 `os.tmpdir()` 길이가 사용자명에 따라 달라진다. 저장소 상대 경로가 그 여유를 넘으면 **격리 Run에서만** 실패하고 비격리 Run은 통과하므로, 격리를 켠 뒤에야 드러나는 종류다.

측정값과 조건을 담아 **P1-31로 등재**했다. 원래 D-1이 같은 것을 가리켰는지는 확인할 수 없고, 그렇게 표시했다.

## 재발 방지 제안 (결정하지 않음)

이번 유실은 슬라이스 사이가 아니라 **감사 문서 → 첫 슬라이스** 구간에서 일어났다. 항목 파일의 권고 중 SUMMARY의 번호 목록에 오르지 못한 것은 그 문서 안에서만 살아 있다가 사라진다. 슬라이스는 SUMMARY를 작업 목록으로 읽지 항목 파일을 훑지 않기 때문이다.

제안하는 절차는 하나다:

> **감사를 종료하기 전에, 항목별 파일이 서술한 모든 권고·발견·"등재만" 항목이 SUMMARY의 P0/P1 번호 체계에 실제로 올랐는지 대조하고, 그 대조 결과를 별도 파일로 남긴다. 번호를 받지 못한 항목이 하나라도 있으면 번호를 부여한 뒤에 감사를 닫는다.**

근거는 이 감사가 만든 두 숫자다. 2026-08-11 감사에서 번호를 받지 못한 항목은 1건이었고 그 1건이 4개 슬라이스 전체에서 사라졌다. 이번 감사에서는 6건이었다 — 대조하지 않았다면 여섯 배로 반복됐을 것이다.

이 규율은 이 저장소가 이미 쓰는 형태와 같다. `scripts/check-rule-coverage.mjs`가 "클레임 없는 규칙에 상태 항목이 없으면 실패"시키는 것과 같은 종류의 대조이고, 다른 점은 대상이 FINAL RULE이 아니라 감사 권고라는 것뿐이다.

**`CLAUDE.md`에 넣을지는 결정하지 않았다.** 그것은 이 저장소의 작업 규칙을 바꾸는 일이고, 규칙 추가는 이 감사의 범위가 아니다. 판단 재료만 남긴다:

- **넣을 이유**: 유실이 실제로 일어났고 비용이 4개 슬라이스였다. 규칙이 없으면 다음에도 같은 자리에서 새어 나간다.
- **넣지 않을 이유**: `CLAUDE.md`는 코드 작업 규율을 담고 감사 절차는 담지 않는다. 감사 문서 템플릿 쪽이 더 맞는 자리일 수 있다.
- **기계화 가능성**: 항목 파일에서 "권고" 절을 추출해 SUMMARY의 `P[01]-\d+` 집합과 대조하는 것은 스크립트로 가능하다. 지금은 사람이 읽어 판단한 항목(무해·P0 본체 포함 등)이 섞여 있어 완전 자동화는 어렵고, "번호가 없는 후보"를 뽑아 사람에게 보여주는 데까지가 현실적이다.
