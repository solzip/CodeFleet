## 2. 파이프라인이 실제로 어디까지 동작했는가

두 번의 실사용 시도가 있었고 **결과가 서로 다르다.** 섞으면 안 된다.

### 2-1. 통제된 fixture — 완주했다

근거: `docs/runs/2026-08-13/first-full-loop.md`. 대상은 `C:\cf-fixture`(ASCII 경로, 파일 3개, git 저장소).

**성공한 것**:

- `init` → `task validate` → `task approve` → `objective create/attach` → `objective run-next` → `review`(waiver) → `import-review` → `apply` 전 단계 통과
- 에이전트(`claude` CLI)가 격리된 git worktree에서 실제로 파일을 편집했고, **계약(역할·상한·Objective 맥락·검증 조건)을 본 상태**였다 (`docs/runs/2026-08-13/p1-53-contract-delivery.md` B-1)
- 검증 커맨드 `node test/check.js`를 **Harness가 직접 실행**해 exit 0을 관측했다(`authority: HARNESS_EXECUTED`). 에이전트가 스스로 같은 커맨드를 돌린 기록은 `PROVIDER_REPORTED_ONLY` / `notCommandTruth: true`로 따로 저장돼 **게이트에 쓰이지 않았다**
- 워크스페이스가 실제로 바뀌었다. `git diff HEAD`가 Harness가 관측한 `git-diff.patch`와 **바이트 단위로 동일**했고, 원장의 `patchRef.hash`를 재계산해 일치를 확인했다
- 격리 트리는 디스크와 `git worktree list` 양쪽에서 폐기 확인
- 무면제 `ACCEPTED`가 `exit=1`로 **실제로 거부**됐다

**성공을 위해 우회한 것 4건** — 이것들이 없으면 완주하지 못한다:

| # | 우회 | 왜 필요했나 |
| --- | --- | --- |
| 1 | 역할을 `INFRA_OPERATOR`로 | Core 역할 7개 중 `COMMAND_EXEC`가 상한인 것은 2개뿐이고, **애플리케이션 코드를 쓰는 역할은 하나도 그 안에 없다**. 백엔드 코드 작업에 인프라 운영자 역할을 붙였다 |
| 2 | `allowDegradedCommandObservation: true` | 이 값 없이는 `COMMAND_EXEC` Run이 계획 단계에서 무조건 차단된다 |
| 3 | 어댑터 인자에 `--permission-mode acceptEdits` | 기본 인자로는 내부 CLI가 파일 편집을 전부 거부한다. **`fileEdit: true`로 기동한 어댑터가 파일을 못 쓴다** |
| 4 | `apply --check` 생략 | 인자 파싱 순서 결함으로 **어떤 인자 조합으로도 실행되지 않는다** |

### 2-2. 실제 프로젝트(Spring Boot) — 완주하지 못했다

근거: `docs/audits/2026-08-12/10-first-real-run.md`. 15단계 중 **차단 4건 + 실패 1건**.

| 단계 | 결과 |
| --- | --- |
| 5 | **차단** — 명령 채널 없음 |
| 6 | **차단** — 격리 |
| 7 | **차단** — 어댑터가 실행 거부 (역할 상한) |
| 9 | **차단** — `cmd /c gradlew.bat` → `SHELL_INTERPRETER_DENIED` |
| 10 | **실패** — gradle은 돌았으나 toolchain 없음 |
| 11 | 통과 — `--version`으로 게이트 `SATISFIED` |

11단계가 이 프로젝트의 성격을 가장 잘 보여준다. **`gradle --version`이 검증 게이트를 만족시켰다.** 그리고 그 사실이 사람이 읽는 문서에 적히지 않아 P1-35로 등재됐다.

그 문서의 결론은 다음과 같다:

> **원장은 `VERIFIED`인데 코드는 어디에도 없다.** 남은 것은 `git-diff.patch` 하나다. … **한 바퀴를 다 돌아도 저장소는 변하지 않는다.**

### 2-3. 그래서 무엇이 참인가

**파이프라인은 통제된 조건에서 한 번 완주했고, 실제 프로젝트에서는 완주하지 못했다.** 완주한 한 번도 우회 4건을 얹은 것이다. "동작한다"고 요약하면 거짓이고, "동작하지 않는다"고 해도 거짓이다.

## 3. 종료 사유

부분 수정으로 해소되지 않는 두 가지다.

### 3-1. 제품 정의가 코드보다 나중에 확정되어, 코드가 정의를 강제하지 못한다

정의 문서(`docs/concept-foundation.md`, FINAL RULE 83개)는 코드가 상당히 진행된 뒤에 확정됐다. 그 결과 정의는 **코드가 하는 일을 서술하는 자리**가 아니라 **코드와 대조되는 별도의 문서**가 됐고, 대조는 사람이 감사로 수행해야 했다.

측정된 증거:

- 조건 줄 545개 중 **345개만 통과한 테스트가 인용**한다(63.3%). 나머지 200개는 코드가 만족하는지 아무도 모른다
- 83개 규칙 중 **28개만** 조건이 전부 덮여 있다
- 2026-08-12 `11-model-conformance.md`가 정의 대비 감사를 처음 수행했을 때, **P0 2건(P0-12·P0-13)이 새로 나왔다.** 그중 P0-13은 하루 전 감사가 **코드 주석을 근거로 통과시킨** 항목이었다(`11-model-conformance.md:152`)
- 같은 계열로 P1-39·P1-40·P1-41이 등재됐다 — Draft/Revision 상태 기계가 없고, 실행 결과 상태가 계약 문서 안에 있었으며, Revision 산출물이 존재하지 않았다

정의가 먼저 있었다면 이 셋은 스키마에서 막혔을 것이다. 나중에 확정된 정의는 **이미 쓰인 코드를 판정할 수만 있고 막을 수는 없다.**

### 3-2. 판정 층과 실행 관측 층이 분리되어 있지 않다

같은 모듈이 **관측**(무슨 일이 있었나)과 **판정**(그것이 통과인가)을 함께 수행한다. `src/run.ts` 하나가 3,000줄이 넘으며 그 안에서 Run 계획·어댑터 기동·증거 수집·정책 평가·게이트 산출이 모두 일어난다.

측정된 결과:

- **P1-50** — 리뷰가 `run-record.md`를 다시 렌더링할 때 검증 증거를 넘기지 않아, 완주한 Run의 문서가 **"검증 증거가 생산되지 않았다"는 거짓 문장**을 갖는다. 같은 파일의 다른 두 줄이 그 증거를 링크하고 있다. 관측과 서술이 같은 층에 있어 한쪽 호출부만 고쳐도 다른 쪽이 조용히 어긋난다
- **P1-53** — 같은 형태. `renderPrompt`의 두 호출부 중 하나만 계약을 넘겼다
- **P0-7** — 격리를 켰더니 증거가 **엉뚱한 트리에서** 수집됐다. 관측 지점이 실행 지점과 분리돼 있지 않아 생긴 결함이고, 그 수정이 다시 P0-8~P0-11을 낳았다

이 구조에서는 **"관측이 옳은가"와 "판정이 옳은가"를 따로 시험할 수 없다.** 하나를 고치면 다른 하나가 움직인다. 2026-08-13의 세 작업(P1-53, P1-61, 배너 순서)이 전부 이 형태였다.
