# 작업 기록 규약 — 전문

이 문서는 `CLAUDE.md`의 「작업 기록 규약」 절의 전문이다. 규칙마다 **그 규칙이 필요해진 실제 사건**을 붙였다. 사유 없는 규칙은 나중에 지워지고, 지워진 뒤에는 왜 있었는지 아무도 모른다.

이 규약 자체가 한 사건의 결과다. 2026-08-13에 감사 2건(`12-waiver-conformance.md`, `13-output-fidelity.md`)을 작성했는데, 그 결론이 편입될 `SUMMARY.md`가 그날 디렉터리에 없었다. 2026-08-12까지의 요약표는 2026-08-13의 판정을 알지 못한 채로 남아 있다. **판정은 났고, 갈 곳이 없었다.**

---

## 1. 기록은 채팅과 별개다

> 감사·수정·실행 작업을 하면 채팅 응답과 별개로 반드시 파일에 기록한다. 채팅에만 답하고 끝내는 것은 작업 미완료다.

**사건**: 2026-08-13 세션에서 P1-50(산출물 거짓 문장)을 발견한 경위는 채팅 대화였다. 지시에 "출력: docs/audits/..."가 없었다면 그 판정은 세션과 함께 사라졌을 것이다. 같은 세션의 다른 판정 — `codefleet prompt`가 Run과 다른 문서를 쓴다는 것 — 도 지시가 있어서 남았다.

채팅 응답은 검색되지 않고, 커밋에 붙지 않고, 다음 세션이 읽지 않는다.

## 2. 위치와 파일명

> 감사(읽기 전용 판정)는 `docs/audits/YYYY-MM-DD/NN-slug.md`, 실행·수정 작업은 `docs/runs/YYYY-MM-DD/slug.md`. 같은 날 재실행은 덮어쓰지 않고 `-v2`, `-v3`.

**사건 A — 번호 충돌**: `docs/audits/2026-08-12/`에 `12-model-conformance-recheck.md`와 `12-orchestration-roadmap.md`가 **둘 다 12번**으로 존재한다. 어느 것이 먼저인지 파일명으로 알 수 없다.

**사건 B — 결번**: 같은 디렉터리가 `01`~`04` 다음 `09`로 건너뛴다. `05`~`08`은 없다. 쓰다 만 것인지, 지운 것인지, 애초에 없던 것인지 판별할 근거가 남아 있지 않다.

**사건 C — 연번이 일자별이 아님**: `docs/audits/2026-08-13/`이 `12-`, `13-`으로 시작한다. 전날 시퀀스를 이어 붙인 것인데, 규약상 일자별 `01`부터여야 한다. **이 두 파일은 이미 다른 문서가 참조하고 있으므로 개명하지 않고, 알려진 이탈로 기록한다.**

덮어쓰기 금지는 사건이 아니라 예방이다 — 같은 날 두 번 판정하면 첫 판정이 왜 뒤집혔는지가 증거의 일부다.

## 3. 상단 메타데이터에 예외를 두지 않는다

> 작업 일시 / 대상 커밋 해시 / 작업 유형 / 선행 문서 경로 / 번호 실측 최대값

**사건**: `docs/audits/2026-08-12/02-handoff-inventory.md`와 `09-registration-check.md`에 **대상 커밋 해시가 없다.** 두 문서의 판정이 어느 코드 상태에 대한 것인지 지금 확정할 수 없다. 같은 날 다른 문서들은 `244fac7`, `9bbfcbf`, `b750e9e`, `5d989f1`, `57a80de`, `c325dec`, `282ad2c`로 서로 다른 해시를 적고 있으므로, "그날의 HEAD"로 추정할 수도 없다.

**선행 문서 경로**가 필요한 이유: 2026-08-13 문서 12는 2026-08-11 `SUMMARY.md:98`의 판정과 모순되는지를 물어서 시작했다. 선행 문서가 명시돼 있지 않으면 그 대조를 매번 손으로 찾아야 한다.

## 4. 하단 필수 절

> 결론(3줄 이내) / 다음 작업(없으면 "없음" 명시) / 미해소로 남긴 것(없으면 "없음" 명시)

**사건**: 2026-08-12에 P1-42~P1-49가 등재됐다. 그 이후 이 8건을 언급한 문서가 하나도 없다. 각 등재 문서에 "다음 작업" 절이 있었다면 끊긴 시점이 문서 안에 드러났을 것이다.

**"없음"을 명시하게 하는 이유**: 빈 절과 없는 절은 다르다. 빈 절은 "확인했고 없다"이고, 없는 절은 "확인하지 않았다"다. 이 구분은 이 제품이 `CAPABILITY_GAP`과 `EVIDENCE_DEFECT`를 나누는 것과 같은 이유로 필요하다.

## 5. INDEX와 REGISTER 갱신

> 매 작업마다 `docs/INDEX.md`에 문서를 추가하고, 등재·등급·상태가 바뀌면 `docs/REGISTER.md`를 갱신한다.

**사건**: 등재된 P0/P1이 68건인데, 전체 목록이 한 곳에 있던 적이 없다. `2026-08-12/SUMMARY.md`가 P0-1~P0-13과 P1-20~P1-41을 담고 있고, P1-1~P1-19는 2026-08-11 문서에, P1-42~P1-49는 2026-08-12의 개별 문서에, P1-50~P1-52는 2026-08-13 문서에 흩어져 있다. **"지금 열려 있는 것이 무엇인가"에 답하려면 39개 문서를 읽어야 했다.**

## 6. 번호는 실측한다

> 프롬프트에 박힌 번호를 그대로 쓰지 않는다. `grep -rhoE "P[01]-[0-9]+"`로 실측 최대값을 확인하고 그 다음부터 부여한다.

**사건**: 2026-08-13 지시가 "새 위반은 P0-14 / P1-39부터 번호를 이어 등재해라"였다. 실측하니 **둘 다 이미 사용 중**이었다 — P0-14는 "Objective relation이 실행되는 revision을 가리키지 않는다", P1-39는 "Draft / Revision 상태 기계가 코드에 없다". 실제 최대값은 P0-16 / P1-49였다. 지시대로 했으면 서로 다른 결함 두 쌍이 같은 번호를 갖게 됐다.

지시자도 사람이고 마지막 상태를 기억하지 못한다. **번호는 기억이 아니라 저장소에서 읽는다.**

## 7. 등급이 바뀌어도 ID는 유지한다

> 등급·상태 변경은 원 문서를 고치지 않고 새 문서에 정정 사실을 기록한다.

**사건 A**: 2026-08-13 문서 13에서 P1-50을 P0 등급으로 재판정했다. ID를 P0-17로 바꾸면 하루 전 문서 12의 P1-50 참조가 전부 끊긴다. **ID는 주소이고 등급은 속성이다.** 주소를 바꾸면 링크가 죽는다. (그 결과 P0-17은 비어 있다 — 이것도 기록해 둔다.)

**사건 B**: 2026-08-13 문서 12가 `first-full-loop.md`의 성공 기준 3을 [충족]에서 [조건부 충족]으로 정정했다. 원 보고서는 고치지 않았다. 이유는 원 보고서가 **인용한 시점의 사실**을 담고 있기 때문이다 — 그때 `run-record.md`에는 검증 커맨드가 적혀 있었고, 리뷰가 그것을 지웠다. 원본을 고치면 "언제 무엇이 사실이었는가"가 사라진다.

## 8. 판정 기준은 제품 정의 문서다

> 코드 주석이 아니다.

**사건**: `docs/audits/2026-08-12/11-model-conformance.md:152`

> "2026-08-11 P0-2 §C-1은 이 동작을 '명시적으로 문서화된 결정'이라며 통과시켰다. 그 판정의 근거는 **코드 주석**이었다. 확정된 정의는 반대를 말하므로, 주석이 아니라 정의를 기준으로 다시 판정한다 — **위반**. → P0-13"

코드 주석은 코드를 쓴 사람의 의도이고, 그 의도가 정의와 어긋나 있어도 주석은 그 사실을 모른다. 통과 판정 하나가 하루 만에 P0로 뒤집혔다.

## 9. 근거 없는 판정 금지 — 파일:라인 필수

**사건**: 2026-08-12 감사 지시가 존재하지 않는 문서(`fixes/env-DESKTOP-ENGO922.md`)와 존재하지 않는 브랜치(`audit/stage3`)를 근거로 판정을 요구했다. 작업 트리·git 히스토리 전체·전문 검색에서 0건이었다. 그때의 처리가 옳았다 — 없는 문서의 내용을 추정해 채우지 않고 코드와 테스트에서 직접 판정했으며, **없다는 사실을 SUMMARY 맨 앞에 적었다.**

## 10. 테스트가 없으면 [부분해소]까지만

**사건**: P1-35(`run-record.md`가 검증 커맨드를 이름으로 적지 않는다)는 2026-08-12에 등재되고 `3873d94`에서 고쳐졌으며, 로드맵에 `[x] S6-3` 완료로 표시됐다. 2026-08-13에 실측한 결과:

- `grep -rn "rests on\|What was verified" test/` → **0건**. 그 절을 단언하는 테스트가 처음부터 없었다
- 리뷰를 마치면 그 절이 사라지고 **거짓 문장으로 대체된다** (P1-50)

**고쳤다는 판정이 테스트 없이 내려졌고, 회귀가 그 자리로 정확히 되돌아왔다.** 코드가 맞아 보이는 것과 맞다는 것은 다르고, 그 차이를 메우는 것이 테스트다.

이 저장소의 `CLAUDE.md`가 이미 같은 말을 하고 있다 — "Verify the verifier. A guard that always returns null looks exactly like a guard that works."

## 11. 테스트 근거는 종료 코드로 적는다

> 통과 건수가 아니라 커맨드 종료 코드로 적는다. 형식은 `npm test > /dev/null 2>&1; echo $?` → `0`. 파이프를 거치면 `$?`가 마지막 명령의 것이 되므로 출력을 버리고 재야 한다.

**사건**: P1-61. `npm test`가 `3db7d64`(S4)부터 `d697aa2`까지 **9개 커밋 동안 종료 코드 1**이었다. 테스트는 전건 통과했고 실패한 것은 posttest의 커버리지 체커였다.

그동안 다섯 개 문서와 커밋 메시지 하나가 테스트 결과를 근거로 인용했다.

| 인용 | 실제 |
| --- | --- |
| `13-system-review.md:17` — "250 통과 / 0 실패 \| npm test" | 통과 건수는 참, **커맨드는 실패** |
| `15-new-module-review.md:179` — "252 통과 / 0 실패" | 같음 |
| 커밋 `c325dec` — "suite 250 passing, 0 failures" | 같음 |

**어느 것도 거짓을 적지 않았다.** 250건은 정말 통과했다. 빠진 것은 커맨드가 0이 아닌 코드로 끝난다는 사실이고, 그것은 통과 건수로는 표현되지 않는다.

측정 방법까지 규칙에 넣는 이유도 사건이 있다. P1-61 조사 중 `npm test 2>&1 | tail -28; echo "exit=$?"`로 종료 코드를 읽고 `0`이라고 적었는데, 그 값은 `tail`의 것이었다. **파이프가 판정을 뒤집는다.**

## 12. 거짓 문장은 미구현보다 무겁다

**사건**: P1-35와 P1-50은 같은 자리에서 일어난 같은 계열의 결함인데 성격이 다르다.

| | P1-35 | P1-50 |
| --- | --- | --- |
| 산출물이 하는 일 | 무엇을 검증했는지 **말하지 않는다** | "**증거가 생산되지 않았다**"고 말한다 |
| 성격 | 침묵 | **거짓** |
| 실제 상태 | `verify-001.json` 존재, PASS | `verify-001.json` 존재, PASS |
| 언제 나타나나 | 항상 | **리뷰를 마친 뒤** = 완주한 Run일수록 나빠진다 |

이 제품의 최종 산출물은 사람이 읽는 문서다. 미구현은 사람이 알아채고 다른 수단을 찾지만, **거짓 문장은 사람이 그것을 믿고 멈춘다.** 등급은 그 차이를 반영한다.

## 이 규약이 적용되지 않는 것

- `docs/concept-foundation.md`, `docs/final-model-architecture.md` 등 **설계 문서** — 판정 기록이 아니라 정의다
- `docs/session-handoff.md`, `docs/design-progress.md` — 상태 문서이고 덮어쓰기가 정상이다
- 코드 주석 — 규약의 대상이 아니지만, **판정 근거로는 쓸 수 없다** (§8)
