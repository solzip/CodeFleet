# CodeFleet — 에이전트가 했다고 말한 일을 어떻게 검증하나

> 실험이다. 2026-08-13에 결과와 비용을 남기고 아카이브했다.
> 유지보수하지 않으며 이슈와 PR을 받지 않는다.

[English](README.md) | 한국어

## 질문

에이전트가 저장소를 고치고 "테스트 통과했습니다"라고 보고한다. 이 시점에 손에 쥔 것은 사실이 아니라 **주장**이다. 그것을 `verified: true`로 저장하는 순간, 게이트를 움직이는 그 값은 **자기를 만든 것이 관측인지 주장인지 더 이상 기억하지 못한다.**

CodeFleet은 이 간극을 구조로 닫을 수 있는지 물었다. 에이전트를 덜 믿는 방식이 아니라, **그 보고가 애초에 판정에 닿지 못하게** 만드는 방식으로.

## 답 — 같은 커맨드, 두 파일

한 번 완주한 Run이 남긴 기록에 파일 두 개가 있다. **둘 다 같은 셸 커맨드를 담고 있다.**

| 파일 | 정체 | 무게 |
| --- | --- | --- |
| `provider-commands.json` | `node test/check.js` — 에이전트가 자기가 돌렸다고 한 진술 | `PROVIDER_REPORTED_ONLY`, `notCommandTruth: true`. **아무것도 움직이지 못한다** |
| `verification/verify-001.json` | `node test/check.js` — Harness가 직접 다시 실행 | `HARNESS_EXECUTED`, `exitCode: 0`. **게이트를 움직인 것은 이쪽** |

에이전트의 보고를 버리지 않는다. **저장하고, 등급을 매기고, 구조적으로 배제한다.** 그리고 그 등급은 플래그가 아니라 **타입**이다.

```ts
type VerificationAuthority =
  "NONE" | "PROVIDER_REPORTED_ONLY" | "HARNESS_OBSERVED" | "HARNESS_EXECUTED" | "WAIVED_BY_POLICY";

// 게이트 계산은 무엇을 읽기 전에 먼저 걸러낸다:
const executed = attempts.filter((a) => a.authority === "HARNESS_EXECUTED");
```

`boolean` 하나에 `source` 필드를 따로 두면 둘이 어긋날 수 있다. 등급 하나짜리 값은 그럴 수가 없다 — **주장이 관측으로 읽히는 상태 자체가 존재하지 않는다.**

이것이 이 프로젝트의 주장 전부였고, 완주한 그 한 번에서는 지켜졌다. 이 페이지의 나머지는 **그 대가**에 대한 것이다.

저 두 파일을 만든 Run은 이렇게 생겼다. Task는 `src/math.js`에 `subtract(a, b)`를 추가하는 것이었고, 검증 커맨드는 그 함수가 없거나 값이 틀리면 실패하도록 짰다. 그리고 **시작 전에 실제로 실패하는 것을 확인했다** — 파일을 안 고쳐도 통과하는 검증은 아무것도 증명하지 못하므로.

```
task approve       → 계약이 sha256(revisionHash, guardrailHash)로 고정된다
objective attach   → 승인된 revision이 큐에 등록된다
objective run-next → git worktree 생성, 에이전트는 거기서만 작업한다
                     Harness가 `node test/check.js`를 직접 실행 → exit 0
                     worktree 폐기
review             → 거부됨: 면제되지 않은 capability gap
review --waive-gap → 수락, DEGRADED / WAIVED_INCOMPLETE로 기록
objective import-review → 결정이 원장에 적재된다
apply              → 관측된 패치를 워크스페이스에 적용
```

`git diff HEAD`가 Harness가 기록한 패치와 바이트 단위로 같았고, 원장의 `patchRef.hash`를 재계산해 일치를 확인했다. 그 적용 시점에 worktree는 디스크에서도 `git worktree list`에서도 이미 사라진 뒤였다 — **패치가 디렉터리가 아니라 증거로 살아남았기 때문에** 반영이 가능했다.

## "그거 그냥 CI 아니야?"

누구나 제일 먼저 묻는 질문이고, **9할은 맞다.** 에이전트 끝난 뒤에 테스트를 직접 돌리면 이것의 대부분을 거의 공짜로 얻는다. 그게 필요한 전부라면 그렇게 하면 된다.

그렇게 해서 못 얻는 나머지 1할이 있고, 그 네 조각이 논쟁할 가치가 있는 부분이다.

- **계약이 실행 후가 아니라 실행 전에 고정된다.** 승인은 Task와 **그 Task가 놓인 정책까지** 함께 해시한다 — `sha256(revisionHash, guardrailHash)`. 나중에 워크스페이스 정책을 바꾸면 그 Run은 거부된다. 승인이 덮고 있던 조건이 더 이상 성립하지 않기 때문이다. 움직인 표적에 CI를 다시 돌리는 것은 **무엇이 합의됐었는지에 대해 아무 말도 하지 않는다.**
- **에이전트가 자기를 판정하는 것을 고칠 수 없다.** 스코프가 `include: src/**`, `exclude: test/**`이고 관측된 변경 파일 목록에 대해 강제된다. 완주한 Run의 기록은 `1 path(s) checked against 1 allowed and 1 denied pattern(s)`이다. CI가 초록이라는 건 테스트가 통과했다는 뜻이지, **에이전트가 테스트를 건드리지 않았다는 뜻은 아니다.**
- **확인하지 못한 것이 누락이 아니라 기록으로 남는다.** CI에서 건너뛴 단계는 대개 그냥 로그가 짧아질 뿐이다. 여기서는 관측 불가능한 채널이 이름 붙은 `CAPABILITY_GAP`이 되어, 사람이 이름을 지목해 서명하기 전까지 수락을 막는다. 그 서명이 사유와 함께 원장에 남는다.
- **결정이 append-only다.** 조용히 참이 될 수 있는 `approved` 필드가 아예 없다. 상태는 이벤트에서 재생되고, 어긋나는 스냅샷은 원장에게 진다.

정리하면 — **CI는 "테스트가 통과했나"에 답한다.** 이 프로젝트가 답하려던 것은 **"이 작업의 기록을 나중에 믿을 수 있나"**였다. 일하는 주체와 보고하는 주체가 같아지는 순간, 이 둘은 다른 질문이 된다.

## 무엇을 알아냈나

이 중 둘은 에이전트와 무관하게 **어떤 백엔드에나 그대로 쓸 수 있다.**

**멱등 키를 호출자가 아니라 의미에서 뽑는다.** 흔한 멱등은 클라이언트가 주는 request id인데, 그건 **클라이언트가 협조할 때만** 동작한다. 여기서는 결과 상태를 실제로 바꾸는 것만 해시하고, 사유 텍스트와 시각은 **일부러 뺀다.** 그래서 같은 결정을 두 번 해도 하나로 접힌다.

```ts
export function computeMutationId(intent: MutationIntent): string {
  const canonical = JSON.stringify([
    intent.mutationKind,
    intent.targetId,
    intent.targetHash ?? "",
    canonicalize(intent.semanticPayload)   // 상태를 바꾸는 필드만
  ]);
  return `mut_${createHash("sha256").update(canonical).digest("hex").slice(0, 16)}`;
}
```

`apply`를 두 번 실행하니 같은 `mut_fa210cedffe0ce00`이 나왔고 이벤트가 늘지 않았다.

**모든 검사가 판정만이 아니라 무엇을 봤는지 함께 보고한다.** 그러지 않으면 `violations: []`이 *다 봤고 없다*와 *아무것도 안 봤다*를 동시에 뜻하고, 둘이 같은 값이 된다. **0건 검사는 통과가 아니라 실패로 다룬다.** 이 원칙이 여기서 조용한 초록 2건을 실제로 잡았다 — CRLF 때문에 규칙 블록을 0개 읽고 성공을 보고한 파서, 그리고 주장을 하나도 기록하지 않은 커버리지 실행.

나머지는 요약만. 각각의 구현과 근거는 [`DESIGN-NOTES.md`](docs/archive/2026-08-13/DESIGN-NOTES.md)에 있다.

이 중 둘은 결국 **하나의 생각을 두 번 말한 것**이었다. 권한 등급과 gap/defect 구분은 둘 다 **"모른다는 것을 데이터로 어떻게 표현하나"**에 대한 답이고, `LESSONS.md`의 결함 유형 일곱 중 셋도 뿌리가 같다 — **없음과 값을 구분하지 않은 것.** 이 프로젝트가 실제로 힘을 쓴 문제는 AI 검증이 아니었다. **부재의 표현**이었다.

버릴 것이 가장 분명한 건 역할 표다. 좁히기만 한다는 원칙은 옳았지만 **파일 편집 권한과 커맨드 실행 권한을 한 축에 매달아서**, 코드를 쓰면서 테스트를 돌리는 기본 역할이 하나도 없게 됐다.

## 이 중 얼마나 확인됐나

짧게 말하면 **위 목록이 시사하는 것보다 적다.** "관측됨"은 대개 **한 번 관측됐다**는 뜻이다.

- **파이프라인은 정확히 한 번 완주했다.** 통제된 fixture에서였고, **우회 4건이 그것을 떠받치고 있었다.** 그중 하나가 역할 바꿔치기다 — 기본 역할 일곱 중 커맨드 실행이 가능한 것은 둘뿐이고, 그 둘 중에 애플리케이션 코드를 쓰는 역할은 없다.
- **실제 Spring Boot 프로젝트에서는 완주하지 못했다.** 열다섯 단계 중 넷이 막히고 하나가 실패했다. 결국 검증 게이트를 만족시킨 커맨드는 `gradle --version`이었다. 우리 구현은 Windows에서 Gradle·Maven wrapper를 부르지 못했다. 셸 인터프리터를 금지하는 규칙 자체는 옳고, 다만 그 규칙 아래로 배치 파일에 닿을 길을 만들어두지 않았다.
- **등재된 결함 77건** — 해소 25, 부분해소 8, 재현안됨 1, 미해소 15, 수용된 한계 1, 그리고 **미확인 27**. 그 27건은 미확인 그대로 닫는다. 등재된 뒤 아무도 들여다보지 않았고, 아직 유효하다고도 아니라고도 말할 근거가 없다.
- `npm test`는 종료 코드 **0**이다(257 통과, 0 실패). 조건 커버리지는 545줄 중 345줄(63.3%)인데, 이는 통과한 테스트가 그만큼을 인용했다는 뜻이지 **그 조건들이 제대로 구현됐다는 뜻이 아니다.**
- CI 워크플로 파일은 있고 **한 번도 돌지 않았다.** 반복·동시성·POSIX에서 시험한 것은 하나도 없다.

> 실행 가능 여부를 보증하지 않는다. 위는 동결 시점의 관측이지 무엇이 동작한다는 주장이 아니다.

## 왜 여기서 멈췄나

부분 수정으로 닫히지 않는 구조적인 이유 둘이다.

**설계가 두 달 앞섰고, 그 설계를 구속력 있게 만드는 장치가 마지막에 왔다.** 설계 문서 90커밋 중 68건이 5~6월에 쓰였고 그때 이미 최종 분량의 4분의 3이었다. **그런데 그중 기계가 검사할 수 있는 형태는 하나도 없었다.** 규칙 블록은 8월 7일에 처음 나타나 8월 10일에 채워졌는데, 그 6일은 `src/` 51커밋 중 49건이 쏟아진 바로 그 기간이고, 규칙과 코드를 대조하는 도구는 그 마지막 날에 도착했다. 설계를 갖는 일과 설계가 코드를 구속하게 만드는 일은 서로 다른 작업이다. 이 저장소는 앞엣것에 두 달을, 뒤엣것에 엿새를 썼다. **63.3%가 그 결과로 남은 간격의 크기다.**

**판정과 관측을 끝내 갈라놓지 못했다.** 한 파일이 3,000줄을 넘기며 Run 계획, 어댑터 기동, 증거 수집, 정책 평가, 게이트 산출을 모두 떠안았다. 이런 모양에서는 "관측이 맞나"와 "판정이 맞나"를 따로 시험할 수 없다. 증상은 정확하다 — 리뷰를 기록하면 사람이 읽는 Run 기록을 다시 렌더링하는데 그 호출부가 검증 증거를 넘기지 않아서, **문서가 "검증 증거가 생산되지 않았다"고 적으면서 두 줄 아래에서 바로 그 증거를 링크했다.** 마지막 날 고친 세 건이 전부 같은 모양이었다.
