## 무엇이었나

CodeFleet은 AI에게 위임한 개발 작업을, 에이전트가 보고한 내용이 아니라 harness가 직접 관측한 증거로 판정하려던 CLI였다. 작업을 범위·역할·가드레일·검증 조건을 담은 계약으로 표현하고, 사람이 승인한 계약만 실행하며, 결과를 diff와 해시와 harness가 스스로 실행한 검증 커맨드로 기록했다. 이 프로젝트가 붙들고 있던 주장은 **에이전트가 자기 작업에 대해 하는 말은 증거가 아니다**라는 것이었다.

## 왜 아카이브했나

구조적인 이유 두 가지다. 어느 쪽도 부분 수정으로 닫히지 않으며, 개별 결함보다 이 두 가지가 읽는 사람에게 값이 있다.

**정의를 코드보다 나중에 썼기 때문에 코드를 구속하지 못했다.** 제품 정의 — FINAL RULE 83개, 조건 줄 545개 — 는 구현이 상당히 진행된 뒤에 확정됐다. 그래서 정의는 코드를 막는 자리가 아니라 코드와 *대조하는* 문서가 됐고, 그 대조는 사람이 감사로 수행해야 했다. 정의를 기준으로 처음 감사했을 때 P0 2건이 새로 나왔는데, 그중 하나는 하루 전 감사가 **코드 주석을 근거로** 통과시킨 항목이었다. 나중에 고정된 정의는 코드를 판정할 수는 있어도 막을 수는 없다.

**판정과 관측을 끝내 분리하지 않았다.** 한 파일이 3,000줄을 넘기며 Run 계획·어댑터 기동·증거 수집·정책 평가·게이트 산출을 모두 담당했다. 이 구조에서는 "관측이 옳은가"와 "판정이 옳은가"를 따로 시험할 수 없다 — 하나를 고치면 다른 하나가 움직인다. 가장 뚜렷한 증상은 이것이다. 리뷰를 기록하면 사람이 읽는 Run 기록을 다시 렌더링하는데 그때 검증 증거를 넘기지 않아, **문서가 "검증 증거가 생산되지 않았다"고 적으면서 두 줄 아래에서 그 증거를 링크했다.**

## 동결 시점의 상태

- **통제된 fixture에서는 파이프라인이 한 번 완주했다** — 승인, 큐 attach, 격리 실행, harness 검증, 리뷰, 반영. 워크스페이스가 실제로 바뀌었고 적용된 패치는 harness가 관측한 것과 바이트 단위로 같았다. **우회 4건이 그것을 떠받치고 있었다.**
- **실제 Spring Boot 프로젝트에서는 완주하지 못했다.** 15단계 중 4건이 차단되고 1건이 실패했으며, 검증 게이트를 만족시킨 커맨드는 `gradle --version`이었다. 우리 구현은 Windows에서 Gradle·Maven wrapper를 호출하지 못했다 — 셸 인터프리터를 금지하는 규칙 때문에 배치 파일에 닿을 길이 없었다.
- **등재된 결함 77건** — 해소 25, 부분해소 8, 재현안됨 1, 미해소 15, 수용된 한계 1, 그리고 **미확인 27**. 27건은 미확인으로 닫는다. 등재된 뒤 아무도 확인하지 않았고, 여전히 유효한지 아닌지에 대한 근거가 없다.
- `npm test`는 종료 코드 **0**이다(257 통과, 0 실패). 조건 커버리지는 545줄 중 345줄(63.3%)이며, 이는 통과한 테스트가 그만큼의 줄을 인용했다는 뜻이지 **그 조건들이 옳게 구현됐다는 뜻이 아니다.**
- CI 워크플로 파일은 있고 **한 번도 실행되지 않았다.**

> 실행 가능 여부를 보증하지 않는다. 위는 동결 시점의 관측이다.
